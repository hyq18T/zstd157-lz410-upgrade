## 1. 刷机前真机状态（只读）

- `/data/adb/modules` 下**没有** `piano_zram`：系统更新后 v1.8 已经不在了，当前是纯净系统状态。
- `zram0`：`lzo [lzo-rle] lz4 zstd` —— 系统默认算法确实就是 **lzo-rle**，与
  `CONFIG_ZRAM_DEF_COMP="lzo-rle"` 一致。这就是第 3 项里新增的“保持默认”所指的东西。
- `/proc/swaps`：`/dev/block/zram0` 16777212 KiB，已用约 5.8 GiB，priority -2；`page-cluster=0`。
- `/proc/crypto`：`zstd` 有 `zstd-scomp` / `zstd-generic`，`lz4` 有 `lz4-scomp` / `lz4-generic`，
  **四个驱动 priority 全是 0** → 新驱动 priority 100 的遮蔽前提在新内核上依然成立。
- 同一份输出里 `lzo-rle-generic` 的 refcnt=9（就是在用的 zram0），而 lz4/zstd 四个驱动 refcnt 都是 1
  → 说明当前系统除 zram 之外没有别的使用方持有这两个算法名，遮蔽的实际影响面就是 zram。
- 已加载模块只有 `binder_prio`、`kshrink_slabd`、`lz4asm`；`binder_prio.ko` 由
  `/vendor/lib/modules` 自带并被系统自己加载。
- `mi_async_reclaim` / `mi_rmap_efficiency` / `ntsync`：新系统里**已经不存在**，也没加载。
- `/data` 是 f2fs，但挂载参数里没有 `compressed`；erofs 的 `EROFS_FS_ZIP=y` 而 LZ4/LZMA/DEFLATE
  全没开 → 系统分区镜像不是压缩的。这两条一起说明：改名遮蔽不会碰到 /data、/system 的落盘数据格式。
- 新系统 `/system_ext/etc/perfinit.conf` 与 v1.8 打包时那份**只差我们自己加的两行**
  （`"page_cluster": 0`、`"comp_algo": "lz4"`），也就是说厂商这份配置在系统更新里没变，
  bind 覆盖方案依然可用。v1.9 的 `perfinit.conf` 是**从当前手机的文件重新生成**的。

## 2. 符号 CRC 核验（这一版的关键）

内核开了 `CONFIG_MODVERSIONS`。任何一个厂商 `.ko` 的 `__versions` 段里存的就是**内核要求的 CRC**，
所以拿真机自带的 `.ko` 反解，比任何外部资料都可靠（段内每项 = `unsigned long crc` + `char name[56]`，
步长 64，小端读前 4 字节即可）。

从 `/vendor/lib/modules` 里拉了模块反解 `__versions`（`qrng_dlkm`、`adsp_sleepmon`、`cifs`、
`aw882xx_dlkm`、`bam_dma` 共 684 条记录，无一条格式异常；`coresight-tmc` 单独用于取 `vmalloc`）：

| 符号 | 6.6.77 写死值 | 6.6.118 实测 | 结论 |
| --- | --- | --- | --- |
| module_layout | 0x4e276f37 | 0x4e276f37 | 一致 |
| vmalloc | 0xd6ee688f | 0xd6ee688f | 一致 |
| vfree | 0x999e8297 | 0x999e8297 | 一致 |
| memset | 0xdcb764ad | 0xdcb764ad | 一致 |
| memcpy | 0x4829a47e | 0x4829a47e | 一致 |
| memmove | 0x5a9f1d63 | 0x5a9f1d63 | 一致 |
| crypto_register_alg | 0x30f4deab | 无厂商导入者 | 取不到，沿用旧值 |
| crypto_unregister_alg | 0x94876ded | 无厂商导入者 | 取不到，沿用旧值 |

- 402 个厂商模块里没有任何一个导入 `crypto_register_alg`/`crypto_unregister_alg`（压缩驱动都是
  编进 Image 的），所以这两个值拿不到实测。CRC 只由类型定义决定，6.6.y LTS 里 `struct crypto_alg`
  不会动，而且最“重”的 `module_layout`（`struct module` 全量展开）已经确认没变，所以旧值可信度高。
- 万一这两个值错了，失败方式是 **insmod 直接被拒 + dmesg 点名是哪个符号**（-ENOEXEC），
  不会崩、不会留下任何状态，属于安全失败。
- 顺带排除了一条歧路：`/proc/kallsyms` 里的 `__crc_*` 只有“模块导出的符号”才有，
  vmlinux 导出的 `vmalloc`/`crypto_register_alg` 没有，所以想靠 kallsyms 读 CRC 是读不到的
  （另外 `kptr_restrict` 默认 2，本次临时改 0 读过一次，读完已还原为 2）。

与 9/19 导出的那份逐字节一致 → 系统更新后内核构建没变，用的就是 `6.6.118` 那套 headers。

ELF 静态核验：

- 两个 `.ko` 的 `.modinfo` 里 `vermagic=6.6.118-android15-8-gc44b714366cc-abogki519650608-4k SMP preempt mod_unload modversions aarch64`
- `version=1.5.7` / `version=1.10.0`，注册名仍是 `zstd` + `zstd-new-generic`、`lz4` + `lz4-new-generic`
- 未定义符号各自只有 7 个：`crypto_register_alg crypto_unregister_alg vmalloc vfree memset memcpy memmove`
  → 与写死的 `__versions` 表一一对应，1.5.7 新增的 `zstd_preSplit.c` 没有引入任何新的内核依赖
- 与 v1.8 里那两个旧 `.ko` 逐字节比对（`cmp -l`）：大小完全相同，各有 **108 个字节**不同，
  分 7 段，全部可解释 —— 82170/82194/82209/82226/82255 五段共 87 字节是 `.modinfo` 里那一条
  vermagic 字符串本身（`77→118`、`ca30f3b4bef6→c44b714366cc`、`440974771→519650608`）；
  84817-84836 那 20 字节是 `--build-id=sha1` 的内容摘要（跟着变是必然）；97297 那 1 字节是
  `.modinfo` 段头的 `sh_size`（新字符串长 1 字节）。**也就是说两版差异只有 vermagic 一处，
  机器码完全同源。**

## 5. 音量键交互改造的测试

在 WSL 里用假 `getevent`（按脚本吐事件）跑了 4 个用例，全过：

| --- | --- | --- | --- |

过程中抓到并修掉一个真 bug：音量键匹配式必须写成 `(KEY_VOLUMEUP|KEY_UP)[[:space:]]+DOWN`。
不带括号时 ERE 里 `|` 优先级最低，等价于「`KEY_VOLUMEUP` 任意行」OR「`KEY_UP…DOWN`」，
于是**松开键的 UP 行也被计数**，一次按键算 2 步 —— 两选项菜单会出现“按了没反应”。
用不带括号的旧写法重跑同一用例，结果确实停在第 1 项，证明测试有效、修复必要。

## 10. 闸门在真机上踩到并修掉的一个坑（重要）

第一版闸门在 WSL 里 6 个场景全过，但**拿到真机 toybox 上直接误判**：

```sh
tr -c '[:print:]' '\n' < some.ko | sed -n 's/^vermagic=//p' | head -1   # Android 上输出为空
```

Android 的 `toybox tr` 跑 `-c '[:print:]'` 会把整段内容压成一堆换行（实测 `od -c` 只剩 `\n\n\n`），
于是读不到 vermagic，**一个本来正确的包会被自己的闸门拦下**。改用：

```sh
grep -ao 'vermagic=[^ ]*' "$ko" | sed -n 's/^vermagic=//p' | head -1
```

`verify.sh` 第 0 步里同一处写法一并修掉（否则它也会永远报 FAIL）。

真机复验（临时把 `kernel-check.sh` + 两个 `.ko` 推到 `/data/local/tmp`，跑完即删，已确认 `ls | grep -c pz_` 为 0）：

```text
uname -r        = 6.6.118-android15-8-gc44b714366cc-abogki519650608-4k
ko vermagic zstd = [6.6.118-android15-8-gc44b714366cc-abogki519650608-4k]   GATE => PASS
ko vermagic lz4  = [6.6.118-android15-8-gc44b714366cc-abogki519650608-4k]   GATE => PASS
把 KC_KO 指向不存在的文件            → GATE 拦住并给出“包不完整/校验 sha256”的说明（真机同样正确）
```

WSL 侧回归同步重跑：10 个脚本 `dash -n` 全过，G/H/I/J/K/L 六场景结论不变。

## 11. 顺带查清的两件事（影响 Piano 补加载逻辑）

- `/vendor/lib/modules/binder_prio.ko` 的 vermagic 其实是 **6.6.57**-android15-8-g9637ff09c728-4k，
  而 `CONFIG_MODULE_FORCE_LOAD is not set`、`CONFIG_MODVERSIONS=y` —— 也就是说这份厂商留在分区里的
  陈旧 .ko **根本不可能被当前内核加载**（`modules.load` 里也没有它）。现在跑着的 `binder_prio`/
  `kshrink_slabd` 是来自别处（第一-stage ramdisk 那份）的匹配版本。
  所以 v1.9 的“系统自带就补加载”加了同一道 vermagic 判断：不匹配就跳过并在 `service.log` 写明原因，
  不再对着陈旧副本刷 `insmod 失败` 的噪音。
- 反过来这也把闸门的前提钉死了：**本内核不允许 vermagic 不符的模块**，所以“内核不对 → insmod 必被拒
  （-ENOEXEC）”不是推测，是 `CONFIG_MODULE_FORCE_LOAD` 未开 + `CONFIG_MODVERSIONS=y` 的必然结果。

## 12. 按你的两点反馈做的修订（最终版）

**a) 输出太宽、要左右滑 → 全部改成窄行**
刷入界面不会自动换行，所以 `customize.sh` 与 `bin/kernel-check.sh` 的**每一行输出**都重排到
26-30 列以内（中文按 2 列算），菜单选项也缩成 `1. lz4` / `2. zstd` / `3. 不改(保持lzo-rle)`。
长字符串（`uname -r`、`.ko` 的 vermagic，都 52 列）用 `kc_wrap()` 按 26 列断行续打。
用脚本量过：`kernel-check.sh` 最长 29 列、`customize.sh` 最长 30 列，刷入界面只需上下滑。
`verify.sh` 是 adb 终端里跑的，终端会自己换行，保留可读的长行。

**b) 第三个菜单的语义我理解错了，已按你的意思拆开**
之前：第 3 项选“保持默认”→ 连新驱动都不加载（等于把第 2 项的选择也推翻）。
现在三项各管各的：第 1 项=MI Piano 调优；第 2 项=**装不装新驱动**；第 3 项=**只决定 zram0 用哪个算法**。
所以“第 2 项启用 + 第 3 项不改算法”= 两个 `.ko` 照常 insmod 注册（`/proc/crypto` 里就在），
只是不覆盖 `perfinit.conf`、不重建 `zram0`、不动 `page-cluster`；要临时用就
`sh bin/zram-algo.sh apply zstd`（它会先确认驱动在位）。只有第 2 项选“跳过”才真的什么都不加载。

改动点：`service.sh` 拆成 `load_drivers` + `switch_zram`（`ZRAM_ON` 与 `ALGO` 两个条件独立判断）；
`customize.sh` 菜单文案与 `description` 同步（`新驱动(已载) zram0不改`）；`verify.sh` 在 default 下
**照旧**跑注册检查和临时 zram refcnt 实证，只取消“zram0 必须等于所选算法”那一条判定；
`post-fs-data.sh` 的 bind 仍只跟 `zram_algo` 走。

## 14. 你装上用起来之后查出的严重问题：新驱动其实一直没在压页

你自己刷进去之后（`/data/adb/modules/piano_zram` 在跑，`zram_algo=zstd`），我读真机状态发现：

```text
driver : zstd-new-generic   priority 100  refcnt 1     ← 我们注册的 1.5.7，没人用
driver : zstd-generic       priority 0    refcnt 9     ← 内置 1.5.2，8 条流正在服务 zram0
zram0  : lzo lzo-rle lz4 [zstd]     mm_stat: 2133012480 orig / 533534434 comp
```

`service.log` 里那行 `zram0 already zstd, no rebuild` 就是病根：`post-fs-data.sh` 的 perfinit bind
让 zram0 开机即以 **zstd** 建立，但那一刻我们的 `.ko` 还没加载（加载在 `service.sh`，late_start），
于是 zram0 拿到的是内置 `zstd-generic`；等 `service.sh` 再跑 `zram-algo.sh apply` 时，它只比较
“算法名对不对”，一比就相等 → 跳过重建 → **新驱动永远轮不到**。
v1.8 的 `验证记录` 里同样写着 `zram0 already lz4, no rebuild` —— 也就是说自 v1.8 起 zram0 从来没被
新驱动服务过，当时的 PASS 只证明了“新驱动能被临时 zram 用上”，没证明“zram0 用的是它”。

### 修法（三处，都已实现并测过）
1. **`post-fs-data.sh` 提前注册驱动**：在 perfinit 建 zram0 之前就 `insmod` 两个 `.ko`，
   第一次建立 zram0 就直接命中新驱动，正常开机不再需要 swap 重建。
2. **`zram-algo.sh` 判据从“算法名相等”改成“新驱动真的在服务”**：读 `/proc/crypto` 里
   `zstd-new-generic`/`lz4-new-generic` 的 **refcnt**，只有 >1 才算在用；否则即使命令行显示已是
   zstd 也强制 `reset→设算法→disksize→mkswap→swapon` 重建一次，并在重建后再读一次 refcnt 记进日志。
   这样兜住了“万一 post-fs-data 还是晚于 zram 创建”的情况。
3. **第 3 项标签不再引用“当前算法”**（就是你抓到的那个）：系统默认改读 `CONFIG_ZRAM_DEF_COMP`
   （本机实测 `lzo-rle`），当前值单独显示，选项印成 `不改(回/留lzo-rle)`。

### refcnt 解析函数的验证
把交付脚本里那段 awk 原样抽出来跑三处：真机 toybox awk + 真 `/proc/crypto` → `zstd=1 / lz4=1 /
不存在=空`（正是诊断值，也正好触发“强制重建”分支）；WSL mawk、gawk 对着 refcnt=9 的样例 → `9`。
